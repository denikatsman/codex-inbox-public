# Attention and activity history

Opening an alert and handling it are independent. A notification starts in Needs attention and Unseen. Each explicit opening click and its Seen state commit before the OS is asked to navigate; acceptance and failure are separate activity records. Opening cannot remove the alert. Mark unseen does not reopen it, and Done does not invent a reading event. A later message in the same host/task, an explicit recorded answer, or manual Done can remove it. Reopen returns it without erasing earlier actions.

The “message sent afterward” rule deliberately matches a proxy for returning to work. It does not claim the message answered every outstanding question. Empty/skipped question responses and rejected steering messages do not count. Request disappearance and timer expiry carry no such implication. Replay of an already observed message cannot undo a later manual Reopen.

## Storage and chronology

`activity.sqlite` lives in `~/Library/Application Support/Codex Inbox/`. Its SQLite activity table is an append-only journal, linked to notifications and stable host/task/project identities. The notices and tasks tables are the current state used by the UI. State changes and corresponding journal entries commit in one transaction, with WAL journaling and full synchronous writes. Storage failures remain visible and stop subsequent writes and opening attempts.

Every journal entry has a permanent increasing sequence number. History displays capture order, newest first. Recovered events also retain their original source timestamp; this separates “Codex recorded this yesterday” from “the inbox recovered it today.” Notifications, source messages, clicks, opening results, manual actions, answer/request updates, and known task/project changes remain linked. Renames and project moves do not overwrite identity snapshots on earlier entries. Historical project knowledge is assigned, explicitly projectless, or unknown. Current metadata cannot establish an unknown historical assignment. History builds its project catalog from retained activity, so a former project remains selectable after its last task moves.

There is no threshold, expiry, or automatic deletion. The UI initially loads 100 matching rows and offers more; querying and writing run on a serial background queue. Large histories use more disk over time. A recovery window covers both changed items and terminal turns in one read-only source snapshot. Its cursor is saved only after both streams finish and their emitted records commit. Item update ordinals select recovery work; original item ordinals establish action order. A turn ending uses its terminal ordinal. Replays retain durable identities and cannot override a later manual decision merely because they were captured later.

The native pipe reader uses 64 KiB chunks and permits one decoded envelope awaiting storage completion. Historical payloads do not accumulate in collector caches. Individual source records/envelopes above 16 MiB hold back the affected coverage and produce a visible warning; they are not truncated or silently skipped. Invalid embedded answer markup remains ordinary message text. A transport/decode/storage failure prevents unsafe checkpoint acknowledgement.

Banner attempts and their accepted/failed results also live in the activity journal. Acceptance means macOS accepted scheduling, not that a person saw a banner. A failed or interrupted attempt remains visible and can be retried explicitly; an interrupted attempt is unknown, not silently retried after restart. Retry preserves the notice's attention state and does not replay independent sound.

Legacy `inbox.json` and, if present, `inbox-v1-preserved.json` are read once and left byte-for-byte intact. The migration unions their notification IDs, with the latest file's state taking precedence. Previously Seen unresolved questions/input/approvals return to Needs attention. Other legacy Seen entries are retained as previously Seen, not relabelled as evidence of a click or reply. History-only recovery also leaves alerts pending unless a recorded later message or answer settles them. Migration is transactional and idempotent. Neither this migration nor a future clock check can reconstruct timestamps that were never recorded, or guarantee recovery of entries already deleted by v1.

## Views and bulk actions

The navigation sidebar, shared project menu and search operate on one set of records. Notification-type views default to Needs attention and offer Done/All and Seen/Unseen filters. Selecting History on an alert narrows the timeline to that task's full chain. Bulk Select All captures matching IDs beyond the loaded page; later arrivals are excluded. A batch changes projections and appends journal records in one transaction. Undo checks per-field versions and later replies, so it cannot undo newer user or source activity.

The Seen migration uses recorded clicks and legacy Seen flags. It does not invent historical times. Recently opened is a projection of the latest durable Inbox click per host/task; attempt IDs prevent late callbacks completing newer attempts. Imported results remain unknown when the journal supplies none.

Task runtime and relationships are stored independently of notifications. The relationship backfill has its own acknowledged cursor and never resets notification recovery. Dot requires Orbit origin metadata; only evidenced creation/spawn edges propagate that classification. Delegation remains separate. Active observations expire to Unconfirmed after 90 seconds without fresh live evidence; disconnect and restart immediately remove live confirmation. None of these events implies completion. Inactive ancestors provide context without affecting running counts. Cloud coverage ends at tasks revealed by local records or the live stream.

Project metadata is read from native project tables first, then Codex's retained legacy assignments and their canonical ID mapping. Unassigned tasks can match unique saved project roots, with explicit projectless flags respected. A folder name alone is never treated as a project. A transient settings-read failure keeps previously known assignments and reports a warning.

## Clock behavior

The utility makes a small HTTPS HEAD request to Apple's connectivity-check page at startup and every six hours. Automatic restarts within one minute do not repeat the request; the settings menu also allows a manual check. No task content, IDs, or account credentials are sent. There are no model or inference calls.

The HTTP Date header provides an approximate network reference. Responses with an excessive cache age or round-trip time are rejected. A discrepancy above 30 seconds produces a visible warning. New activity uses the checked reference plus continuous elapsed time, which ignores manual wall-clock changes during that run and advances across sleep. Device time, effective time, elapsed time, session identity, and clock quality are all retained; original Codex timestamps are kept separately. Old events are never silently redated, and the permanent sequence preserves capture order even across clock corrections.

Offline collection continues. Before a successful check, timestamps are explicitly labelled as device time; after a stale reference, they are labelled estimated. This is a sanity check, not signed, precision, or independently auditable time. It never changes the Mac's clock or settings. Existing Codex timer estimates retain their source meaning; a clock check does not turn an estimated panel countdown into an exact answer deadline.
